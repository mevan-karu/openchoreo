Thanks for this. It's one of the most carefully put together issues we've had, and verifying each workaround against a live instance saved us a lot of guessing. Your diagnosis is right on every technical point, and Authentik isn't doing anything wrong here.

Per-provider issuers are spec conformant. [RFC 8414 §2](https://www.rfc-editor.org/rfc/rfc8414.html#section-2) defines the issuer as "the authorization server's issuer identifier", so the issuer string is the identity of an authorization server rather than a label attached to a client. Two issuers therefore mean two authorization servers by definition, and [§3](https://www.rfc-editor.org/rfc/rfc8414.html#section-3) says so directly: "Using path components enables supporting multiple issuers per host. This is required in some multi-tenant hosting configurations." Structurally your setup is the same as Okta custom authorization servers or Keycloak realms. Authentik just provisions one per application by default instead of making you opt in. Your reasoning on global issuer mode is correct too, since the discovery document has to be served at the same issuer you appended the well-known path to ([RFC 8414 §3.3](https://www.rfc-editor.org/rfc/rfc8414.html#section-3.3), [OIDC Discovery §4.3](https://openid.net/specs/openid-connect-discovery-1_0.html#ProviderConfigurationValidation)) and Authentik only serves it per application. That means `occ` deriving discovery from the issuer is right, and global mode is what breaks.

What stops us adding a trusted issuer list isn't the `iss` comparison. That line is easy to change. It's that a second issuer means a second authorization server, and OpenChoreo currently has no way to tell whether two authorization servers are backed by the same user base with the same entitlements. Our authorization model assumes they are. Role bindings match on entitlement claims without qualifying them by issuer, so a token asserting `groups: ["platform-admin"]` gets the matching role whichever issuer minted it. Yours share a directory, but that's your knowledge of your own deployment rather than something we can verify, and a shared directory isn't sufficient on its own. In Authentik the `groups` claim comes from a scope mapping expression, `[group.name for group in request.user.groups.all()]` in the default `profile` mapping, and [scope mappings are selected per provider](https://docs.goauthentik.io/add-secure-apps/providers/property-mappings/). Two providers over one user base can therefore be configured to emit different `groups` for the same person. Same users, different entitlements, and the authorization decision changes depending on which provider issued the token. That difference is invisible to us, so relaxing the issuer check would fail quietly, with wrong authorization rather than a clean error.

For now the thing we'd suggest is federation. If Authentik sits behind an IdP that can federate it as an upstream provider, OpenChoreo sees one issuer over one user base with one set of entitlements, which is the topology the authorization model is built for. Most IdPs that support identity brokering will do this, and it keeps interactive login with real per-user identity and groups intact. I would avoid `occ login --client-credentials` for human users, for the reasons you already set out. Losing per-user identity, group mapping and audit attribution is a worse outcome than the problem it solves.

This isn't a permanent no. If we support multiple issuers we want to do it properly rather than by widening the issuer check, and properly means issuer scoped entitlements, so a role binding can say which issuer it trusts for a given claim, along with the metadata and client side work to let each client find the right authorization server. That's a design discussion we haven't had yet. If you'd like to open a separate issue for it I'd be glad to take part, and your Authentik setup is a good motivating example to anchor it. You were also right that this is a different request from #1636 and #1741. Those removed a second way to name one issuer. What you're asking for is a different thing, and the reason we're saying not yet is the authorization model, not config hygiene.

Sorry this isn't the answer you were hoping for. The report was genuinely excellent and it's pushed us to write down an assumption we'd never made explicit.
